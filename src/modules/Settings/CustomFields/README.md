# Модуль «Динамические поля» (Custom Fields)

Документ-передача для следующего разработчика/ИИ. Описывает, **что уже сделано**,
**как устроено** и **что делать дальше**.

---

## 1. Что это и в каком состоянии

Справочник дополнительных (динамических) полей для таблиц HRMS. HR может добавлять
к существующим таблицам свои поля, задавать им тип и правила валидации — без правок кода.

**Модуль сознательно ограничен CRUD-ом полей.** Расположения в форме здесь нет:
карточек формы, ширины поля, drag-n-drop-сортировки и предпросмотра формы **больше нет**
(убрано по требованию заказчика). Расположение настраивается **в самой форме**:
кнопка «Настроить форму» на `/employees/new` — см.
`src/modules/Employees/Form/layout/README.md`.

**Текущий этап — второй: подключён API, но только справочник полей и только
таблица `user_base`.** Схема живёт в БД (`hrms_custom_fields`), ходим через
cloud-функции `custom_fields_*` в `udevs-hrms-reports` — описание в
`udevs-hrms-reports/CUSTOM_FIELDS_DB_SCHEMA.md`. Остальные таблицы показаны
вкладками с замком (`entity.enabled === false`).

**Значения динамических полей ещё не сохраняются** — форма сотрудника поля
рисует, но в payload их не кладёт (колонки под них в u-code нет; предложение —
поле `custom_data` типа JSON у `user_base`, см. раздел «Дальше» в схеме БД).

Страница: `/settings/custom-fields`
Регистрация: пункт `custom-fields` в `src/modules/Settings/index.tsx` (секция
«Основные настройки») + роут в `src/App.tsx` внутри блока `<Route path="/settings">`.

## 2. Модель данных

Два уровня: **сущность (таблица) → поле**. Типы в `types.ts`.

```
CustomFieldEntity   id/slug таблицы (user_base, candidates, vacancies, employee_works, properties)
  └── CustomField   key, label, type, placeholder, hint, defaultValue, options[],
                    directorySlug, rules{...}, system, sortOrder
```

Каталог таблиц и статичные поля приходят **с сервера** (`custom_fields_list`),
а не хардкодятся во фронте — так список защищённых ключей всегда совпадает с тем,
что валидирует сервер.

### Ключевые соглашения

- **`system: true`** — статичное поле таблицы, которое уже описано в коде формы
  (например, `first_name` в `user_base`). Такие поля:
  - **показываются в списке первыми, но защищены** (бейджи «статичное» / «защищено»):
    строка некликабельна, тумблера и меню действий нет;
  - нужны для **проверки уникальности ключа**: нельзя завести динамическое поле
    с ключом уже существующей колонки (сервер проверяет то же самое по
    `information_schema`, так что обойти через API не выйдет).
- **`id`** динамического поля = `guid` строки в БД; у статичных — синтетический
  `sys_<таблица>_<ключ>`. Новое поле до сохранения имеет временный `fld_…`, по
  которому сервис и понимает, что это создание.
- **`sortOrder`** — сквозной внутри таблицы; статичные поля идут первыми
  (сервис сдвигает `sort_order` динамических на их количество). Порядок в UI
  не редактируется, поле просто добавляется в конец.
- **Ключ поля нельзя переименовать** после создания — сервер отклонит: значения
  уже сохранены под старым ключом.

## 4. UX-решения (не ломать без причины)

1. **Мастер из 2 шагов.** Новое поле: шаг 1 — «Какое поле добавить?» (плитки типов),
   шаг 2 — настройки. У существующего поля шагов нет, тип меняется кнопкой «Изменить тип».
   Флаг — `typePicker` + `isNewFieldRef` в `FieldEditorModal`.
2. **Живой предпросмотр** внизу модалки («Так поле увидит сотрудник») — переиспользует
   `FieldControl`, поэтому всегда совпадает с реальным рендером контрола.
3. **Клик по строке поля** открывает редактор; клики по кнопкам внутри строки
   не всплывают (проверка `closest("button")`).
4. **Автоключ**: «Размер обуви» → `razmer_obuvi` (транслитерация в `utils.slugifyKey`),
   пока пользователь не отредактировал ключ вручную (`keyTouchedRef`).
5. **Ширина контента.** Страница живёт внутри лейаута настроек (сайдбар приложения +
   сайдбар настроек), контенту остаётся ~900px. Поэтому выбор таблицы — горизонтальные
   вкладки, сводка — одна строка, сетки адаптивные (`md:grid-cols-2`).

## 5. Проверка кода в этом репозитории

⚠️ **`npx tsc -p tsconfig.app.json --noEmit` бесполезен**: он падает на
`TS2688: Cannot find type definition file for 'react-datepicker'` и **прекращает
проверку**, поэтому вывод выглядит «почти чистым», даже когда есть реальные ошибки
(так однажды пропустили ссылку на удалённую переменную → белый экран).

Реальная проверка:

```bash
# временный конфиг с "types": [] (иначе tsc обрывается)
npx tsc -p <tmp>/tsconfig.check.json --noEmit | grep CustomFields
npx eslint src/modules/Settings/CustomFields
npx vite build
```

И обязательно — прогон страницы в браузере.

Пакетный менеджер: **yarn** (Dockerfile делает `yarn install --frozen-lockfile`).
`package-lock.json` тоже присутствует — после `yarn add/remove` синхронизируйте его
через `npm install --legacy-peer-deps --package-lock-only` (обычный `npm i` падает
на конфликте peer-зависимостей `react-datepicker` ↔ React 19).

## 6. Что дальше (следующие этапы)

1. **Значения полей.** Форма сотрудника уже рендерится по раскладке
   (`src/modules/Employees/Form/layout/`) и умеет показывать динамические поля;
   значения в payload пока не кладутся — колонки под них в u-code нет.
   Предложение: одна jsonb-колонка `user_base.custom_data` + метод
   `custom_fields_values_save` (раздел «Дальше» в `CUSTOM_FIELDS_DB_SCHEMA.md`).
2. **Остальные таблицы.** Кандидаты, вакансии, трудоустройство, имущество —
   снять `enabled: false` в `ENTITIES` (`custom-fields-common.js`) и описать их
   `systemFields`. Фронт менять не нужно.
3. **Валидация на сохранении записи** по `field.rules` (сейчас правила только
   описываются и показываются чипами).
